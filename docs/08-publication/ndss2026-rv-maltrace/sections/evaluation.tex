\section{Evaluation}
\label{sec:evaluation}

We evaluate \rvmt on five research questions: trace correctness, source-label
coverage, code-attribution accuracy, reconstruction under software-tracer
visibility, and artifact reproducibility. The evaluation is organized around
quantitative claims with specific metrics and explicit claim boundaries.

\subsection{Experimental Setup}
\label{subsec:experimental-setup}

\textbf{Platform.}
All experiments run on a CVA6/Genesys2 FPGA board with the trace adapter described in Section~\ref{subsec:trace-adapter}. The board runs a RISC-V Linux kernel and user-space runtime. Trace records are collected through the BRAM buffer and transferred to the host for offline reconstruction.

\textbf{Workload suite.}
We use a suite of controlled synthetic and malware-like workloads that exercise
the trace path and reconstruction pipeline. The workloads cover: file creation,
open, read, and write operations; process creation via \texttt{fork},
\texttt{execve}, and \texttt{clone}; dynamic library loading and unloading;
anti-debug-like behavior using \texttt{ptrace} and \texttt{/proc/self/status};
and syscall sequences that include \texttt{open}, \texttt{read}, \texttt{write},
\texttt{close}, \texttt{socket}, \texttt{connect}, and \texttt{execve}. These
workloads are designed to test event ordering, syscall pairing, privilege
transitions, code attribution, and controlled anti-analysis reconstruction.

\textbf{Reference tools.}
We validate trace behavior against QEMU instruction traces and \texttt{strace} syscall logs. QEMU provides an expected instruction stream for the same workload; \texttt{strace} provides an expected syscall sequence. These references are used to validate correctness, not to report hardware-derived results.

\textbf{Metrics.}
We report: (1) trace correctness---pass/fail status of directed tests; (2)
source-label coverage---percentage of reconstructed fields with correct
provenance labels; (3) code-attribution accuracy---percentage of PC events
correctly attributed to their owning executable; (4) software-tracer visibility
versus hardware-backed reconstruction for controlled anti-analysis workloads;
and (5) reproduction status and manifest coverage for the artifact package.

\subsection{RQ1: Trace Correctness}
\label{subsec:rq1-trace-correctness}

RQ1 asks whether the CVA6 trace adapter correctly captures and orders architectural events. We answer it with a suite of directed tests that exercise the adapter against every event category and several edge cases.

The checker reports 50 directed correctness cases, 10 seeded-random
event-sequence cases, and 9 negative-sensitivity cases. All 69 cases pass,
confirming correct event ordering and syscall pairing. Table~\ref{tab:trace-correctness}
summarizes the test categories and their results.

The trap/retire and privilege-context tests confirm that traps, following
instructions, and privilege changes are recorded as distinct events at the
correct instruction boundary. The strict syscall pairing tests confirm that every
syscall entry record is matched by a return record with no unpaired events. The
same-cycle and dual-commit ordering tests confirm that the record stream respects
architectural commit order even when the pipeline retires multiple instructions
per cycle. The negative sensitivity cases confirm that injected violations such
as unqualified SRET returns, syscall-pairing breaks, and same-cycle ordering
errors are rejected by the checker.

\subsection{RQ2: Source Labeling}
\label{subsec:rq2-source-labeling}

RQ2 asks whether every reconstructed field carries a correct provenance label. We verify that each field in the output behavior summary is labeled with its evidence source: hardware trace, ELF metadata, runtime map, or reference log.

Our results show that 288/288 provenance-tagged fields (100\%) are correctly
labeled across 12 sample artifacts. The provenance summary records 12 hardware
trace-source fields and 276 validation-oracle fields, with allowed labels
\texttt{hardware}, \texttt{exact\_elf}, \texttt{runtime\_os\_map}, and
\texttt{validation\_oracle}. We further verify that reference-derived fields are
never mislabeled as hardware-derived. No reference-derived fields are incorrectly
reported as hardware output. This separation is enforced by the reconstruction
pipeline: a field that depends on QEMU, \texttt{strace}, or host-control data is
explicitly marked with \texttt{validation\_oracle} provenance and is never
treated as a hardware-derived result.

\subsection{RQ3: Code Attribution}
\label{subsec:rq3-code-attribution}

RQ3 asks whether trace PCs are correctly attributed to their owning executables. We evaluate this with a set of test cases that cover the common failure modes of PC-to-binary mapping.

RV-MalTrace correctly attributes 108/108 key PC events (100\%) to the target
ELF/function level across 12 controlled workload artifacts. Runtime process
attribution is proven for 12/12 artifacts, and dynamic-library separation holds
for 12/12 artifacts. The dynamic-mapping checker also passes 6/6 edge cases
covering static executables, PIE/ASLR load bias, dynamic loader mappings, shared
libraries, stripped binaries, and fork/exec ownership. These cases test both
identity checks---the traced binary must match its SHA-256 identity---and mapping
logic, including load-bias resolution, library attribution, and post-\texttt{execve}
ownership transfer. Stripped binaries degrade to segment/offset attribution
rather than source-line claims. The debug/no-PIE sidecar reaches 100\%
source-line attribution locally, but current board traces remain function-level
unless the exact captured ELF carries DWARF; board-native DWARF source-line
recovery is therefore not claimed.

\subsection{RQ4: Software-Tracer Visibility}
\label{subsec:rq4-evasion-comparison}

RQ4 asks whether \rvmt can still reconstruct behavior when a software tracer is
visible to, or perturbs, a controlled anti-analysis workload. We evaluate this as
a bounded case study rather than as a general invisibility or malware-detection
claim. The software baseline runs the probe under native execution, native
\texttt{strace}, QEMU-user, and QEMU-user with \texttt{strace}; the hardware
evidence comes from the Genesys2 BRAM marker-window trace for the corresponding
safe surrogate workload.

The other two rows in Table~\ref{tab:evasion-comparison} are intentionally
classified as supporting reconstruction rows. They show that the current
hardware traces reconstruct process-chain and dynamic-executable-memory
behaviors, but they do not demonstrate software-tracer failure. We therefore
claim one complete software-tracer-fails/\rvmt-reconstructs row in the current
artifact, not broad evasion resistance for all tracers or workloads.

The board runtime benchmark is useful as a smoke test: the trace-off,
event-only, BRAM-ring, and pointer-snapshot-disabled modes all complete with the
same 9s median UART-marker duration across the benchmarked samples. Because the
metric is derived from board UART \texttt{date} markers, it is too coarse to

single-mode marker-window duration and is not a trace-off comparison. Finally,
the streaming/DMA summaries convert current BRAM traces into a target rate for a

transport has been implemented or validated. The routed trace-enabled design
adds 21,505 LUTs, 9,143 FFs, and 6 BRAM18 equivalents over the baseline report;
the reported timing slack and approximate Fmax are unchanged in the current
routed snapshot.

\subsection{RQ5: Reproducibility}
\label{subsec:rq5-reproducibility}

RQ5 asks whether the reported results are independently reproducible. We
evaluate this with two reproduction paths and a manifest coverage check.

The command \texttt{uv run rvmt repro:quick} is recorded as PASS and runs 18
lightweight checks spanning manifests, archive integrity, semantic provenance,
local code-analysis fixtures, trace correctness, tracer visibility, controlled
evasion comparison, cycle diagnostics, official-image summaries, attribution,
repeatability, hardware-oracle separation, and recursive path/hash integrity.
The Docker path, \texttt{uv run rvmt ndss:docker-full}, is also recorded as PASS
inside the \texttt{linux-behavior} service with an isolated \texttt{uv}
environment. All reported results are backed by SHA-256 verified files: the
reproducibility manifest records 63 summary artifacts and 7 report rows, while
the artifact-package manifest records 240 included files and references 6 raw
artifact roots. The local raw-artifact archive contains 2,033 files
(286,007,909 bytes); any manifest mismatch causes reproduction to fail with a
clear error.

\subsection{Discussion}
\label{subsec:discussion}

The evaluation intentionally separates supported results from open production
claims. First, the current prototype uses BRAM marker-window traces for
controlled workloads; production streaming/DMA throughput remains a future
transport study. Second, the artifact contains board UART runtime smoke and an
FPGA trace-cycle marker-window measurement, but it does not claim cycle-level
trace-off versus trace-on slowdown. Third, real malware validation is not
evaluated; safe synthetic and malware-like workloads test trace behavior under
controlled conditions, but malware-family accuracy and IOC coverage require
separate study. The software-tracer visibility result is likewise bounded: the
current artifact contains one complete anti-debug-like failure/reconstruction
row, plus supporting reconstruction rows that do not claim software-tracer
failure.
