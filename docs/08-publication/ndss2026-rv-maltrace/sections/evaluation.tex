\section{Evaluation}
\label{sec:evaluation}

We evaluate \rvmt on four research questions: trace correctness, source-label coverage, code-attribution accuracy, and artifact reproducibility. The evaluation is organized around quantitative claims with specific metrics.

\subsection{Experimental Setup}
\label{subsec:experimental-setup}

\textbf{Platform.}
All experiments run on a CVA6/Genesys2 FPGA board with the trace adapter described in Section~\ref{subsec:trace-adapter}. The board runs a RISC-V Linux kernel and user-space runtime. Trace records are collected through the BRAM buffer and transferred to the host for offline reconstruction.

\textbf{Workload suite.}
We use a suite of controlled synthetic and malware-like workloads that exercise the trace path and reconstruction pipeline. The workloads cover: file creation, open, read, and write operations; process creation via \texttt{fork}, \texttt{execve}, and \texttt{clone}; dynamic library loading and unloading; and syscall sequences that include \texttt{open}, \texttt{read}, \texttt{write}, \texttt{close}, \texttt{socket}, \texttt{connect}, and \texttt{execve}. These workloads are designed to test the correctness of event ordering, syscall pairing, privilege transitions, and code attribution under controlled conditions.

\textbf{Reference tools.}
We validate trace behavior against QEMU instruction traces and \texttt{strace} syscall logs. QEMU provides an expected instruction stream for the same workload; \texttt{strace} provides an expected syscall sequence. These references are used to validate correctness, not to report hardware-derived results.

\textbf{Metrics.}
We report: (1) trace correctness---pass/fail status of directed tests; (2) source-label coverage---percentage of reconstructed fields with correct provenance labels; (3) code-attribution accuracy---percentage of PC events correctly attributed to their owning executable; and (4) reproduction time---time to complete the quick and Docker-local reproduction paths.

\subsection{RQ1: Trace Correctness}
\label{subsec:rq1-trace-correctness}

RQ1 asks whether the CVA6 trace adapter correctly captures and orders architectural events. We answer it with a suite of directed tests that exercise the adapter against every event category and several edge cases.

The checker reports 50 directed correctness cases, 10 seeded-random
event-sequence cases, and 9 negative-sensitivity cases. All 69 cases pass,
confirming correct event ordering and syscall pairing. Table~\ref{tab:trace-correctness}
summarizes the test categories and their results.

The trap/retire and privilege-context tests confirm that traps, following
instructions, and privilege changes are recorded as distinct events at the
correct instruction boundary. The strict syscall pairing tests confirm that every
syscall entry record is matched by a return record with no unpaired events. The
same-cycle and dual-commit ordering tests confirm that the record stream respects
architectural commit order even when the pipeline retires multiple instructions
per cycle. The negative sensitivity cases confirm that injected violations such
as unqualified SRET returns, syscall-pairing breaks, and same-cycle ordering
errors are rejected by the checker.

\subsection{RQ2: Source Labeling}
\label{subsec:rq2-source-labeling}

RQ2 asks whether every reconstructed field carries a correct provenance label. We verify that each field in the output behavior summary is labeled with its evidence source: hardware trace, ELF metadata, runtime map, or reference log.

Our results show that 288/288 provenance-tagged fields (100\%) are correctly
labeled across 12 sample artifacts. The provenance summary records 12 hardware
trace-source fields and 276 validation-oracle fields, with allowed labels
\texttt{hardware}, \texttt{exact\_elf}, \texttt{runtime\_os\_map}, and
\texttt{validation\_oracle}. We further verify that reference-derived fields are
never mislabeled as hardware-derived. No reference-derived fields are incorrectly
reported as hardware output. This separation is enforced by the reconstruction
pipeline: a field that depends on QEMU, \texttt{strace}, or host-control data is
explicitly marked with \texttt{validation\_oracle} provenance and is never
treated as a hardware-derived result.

\subsection{RQ3: Code Attribution}
\label{subsec:rq3-code-attribution}

RQ3 asks whether trace PCs are correctly attributed to their owning executables. We evaluate this with a set of test cases that cover the common failure modes of PC-to-binary mapping.

RV-MalTrace correctly attributes 108/108 key PC events (100\%) to the target
ELF/function level across 12 controlled workload artifacts. Runtime process
attribution is proven for 12/12 artifacts, and dynamic-library separation holds
for 12/12 artifacts. The dynamic-mapping checker also passes 6/6 edge cases
covering static executables, PIE/ASLR load bias, dynamic loader mappings,
shared libraries, and fork/exec ownership. The test cases include:
\begin{itemize}
\item \textit{ELF identity matching}: the code-map builder matches the traced binary against its SHA-256 identity and rejects mismatched or modified executables;
\item \textit{PIE/ASLR load bias resolution}: the joiner resolves the runtime load address of a position-independent executable and applies the correct bias when mapping PCs to code ranges;
\item \textit{Dynamic object attribution}: the joiner attributes PCs within dynamically loaded shared libraries to the correct library object and version;
\item \textit{Fork/exec ownership tracking}: the reconstruction pipeline tracks process identity across \texttt{fork} and \texttt{execve} transitions, attributing post-exec PCs to the new executable;
\item \textit{Stripped binary handling}: the builder maps stripped binaries by
their ELF segment headers when debug symbols are absent, degrading to
section/offset attribution rather than source-line claims;
\item \textit{Source-map boundary cases}: the debug/no-PIE sidecar reaches
100\% source-line attribution locally, while the current board traces remain
function-level unless the exact captured ELF carries DWARF.
\end{itemize}

Most cases are handled by the reconstruction pipeline using ELF metadata and
runtime maps. Board-native DWARF source-line recovery is not required for the
evaluated attribution and is not claimed for the current board traces.

\subsection{RQ4: Reproducibility}
\label{subsec:rq4-reproducibility}

RQ4 asks whether the reported results are independently reproducible. We evaluate this with two reproduction paths and a manifest coverage check.

\textbf{Quick local reproduction.}
The command \texttt{uv run rvmt repro:quick} is recorded as PASS and runs 17
lightweight checks: reproducibility and artifact-package manifests, raw-artifact
archive integrity, semantic provenance, local code-analysis fixtures, trace
correctness, tracer visibility, cycle diagnostics, official-image workload
summaries, runtime-map attribution, fork/exec ownership, PIE/ASLR probing,
repeatability, hardware-oracle separation, JTAG RAM boot status, and recursive
artifact path/hash integrity.

\textbf{Docker-local reproduction.}
The command \texttt{uv run rvmt ndss:docker-full} is recorded as PASS in the
\texttt{linux-behavior} Docker service. It runs the full reproduction set inside
the container with an isolated \texttt{uv} environment, including Python compile
checks, the \texttt{genesys2-current} suite (76/76), the artifact suite, the
\texttt{genesys2-self-test} suite (102/102), and the
\texttt{ccfa-gate-self-test} suite (52/52).

\textbf{Manifest coverage.}
All reported results are backed by SHA-256 verified files in the evidence
directory. The reproducibility manifest records 62 summary artifacts and 7 report
rows. The artifact-package manifest records 228 included files and references 6
raw artifact roots. The local raw-artifact archive contains 3,356 files
(323,142,849 bytes); the manifest records its full SHA-256 digest, with prefix
\texttt{57f48d6e26959826} and suffix \texttt{8b22f611}.
Any manifest mismatch causes the reproduction command to fail with a clear error
message.

\subsection{Discussion}
\label{subsec:discussion}

We identify three limitations. First, the current prototype uses a BRAM trace buffer for controlled workloads; production streaming throughput and DMA transport are left for future work. Second, cycle-level runtime overhead is not measured because the required live cycle-source path is not yet available on the board. Third, real malware validation is not evaluated; safe synthetic and malware-like workloads test trace behavior under controlled conditions, but malware-family accuracy and IOC coverage require separate study.
